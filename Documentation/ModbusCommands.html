01

The model: two verbs, four areas

Every Modbus operation is a read or a write of an area at an address on a device. The function code is not a command, it is a consequence of the area and the direction — so the command set does not need one spelling per function code.

Devices & transport

The transport leaves the address prefix and becomes part of a named device. Both Ethernet and subnet devices are addressed the same way, the token decides the route.

05

Device handles — the SUB:1.2 case

A subnet device is not a different kind of command, it is a different route to the same commands. MB_DEFINE_DEVICE binds a name to the route once, so a VAV box behind panel 1 and an Ethernet meter are written identically and the dotted prefix leaves the program body.

HandleTransportPanelSlaveToday's formFCsWhat it means
VAV7 SUB:1.2 1 2 1.2. 03 06 10 01 05 0F 02 04 VAV box on the RS485 subnet of panel 1. Panel 1 is the controller whose IP ends in .1; the frame is routed to it and reaches unit id 2 on the subnet. Reads, writes, blocks and coils all work through the one handle.
Meter1 TCP:192.168.0.199:502,TO=500,RT=2 - - 199.x. prefix today 03 06 10 01 05 0F 02 04 Ethernet meter by IP, with its own timeout and retries instead of the global response time.
Pump1 RTU:COM3,9600,N,1,5 - 5 no prefix today, COM port is chosen in the UI 03 06 10 01 05 0F 02 04 Serial device on the PC COM port. The port settings live in the handle, once.
IP:199.4 legacy shortcut, no registration 199 4 199.4. 03 06 10 02 04 The old dotted prefix kept as a token so untouched programs keep working. Panel wins over IP octet on collision.
Worked case · VAV7 at SUB:1.2
MB_DEFINE_DEVICE("VAV7", "SUB:1.2")             // panel 1, slave 2, RS485 subnet, routed transparently

VAR1   = MB_READ ("VAV7", REG, 7)                // FC 03, unit 2 through panel 1 - same bytes as 1.2.MB_REG7
MB_WRITE("VAV7", REG, 3, VAR1)                   // FC 06 - same bytes as 1.2.MB_REG3 = VAR1
VAR100 = MB_READ ("VAV7", REG, 33, 2, F32, ABCD) // FC 03, two registers - replaces MB_REG_FLOAT_ABCD33
VAR107 = MB_READ ("VAV7", COIL, 7)               // FC 01
MB_WRITE("VAV7", COIL, 0, 1, 0, 1)              // FC 0F, three coils - no keyword exists for this today
STA    = MB_LAST_STATUS()                        // 0 ok, -1 timeout, -2 CRC, -5 no device, -6 exception
NEW COMMAND & METHOD MB_DEFINE_DEVICE("VAV7", "SUB:1.2") one handle carries panel, slave, timeout and retries: MBAP to panel 1, unit id 2 in the PDU, panel forwards down its RS485 subnet

A program that used 1.2.MB_REG7 gets byte-identical traffic, so P0 can swap spellings without touching a single device. The handle also carries what the prefix cannot: poll rate, timeout, retries, an optional unit id override and a display name that matches the device tree. Today those live per call (SetResponseTime) or nowhere. AddDeviceDlg becomes the place that writes the registration.

06

Migration plan

Each phase has to leave every existing program working. Legacy keywords stay supported permanently.

P0 · Vocabulary

New verbs as translations onto the existing DLL calls. No change to any frame.
Exit: every new command produces the same bytes as its legacy pair, checked with the _log exports.

P1 · Types

One type system: U16, S16, U32, S32, F32, BIT, and four byte orders.
Exit: eight float keywords become two aliases, and the * 65536 + advice disappears.

P2 · Areas

Coil and discrete areas complete, including 0x05 and 0x0F writes.
Exit: a program can drive a coil through the same verb it reads with.

P3 · Entry point

Collapse _2, _nocretical and _tap onto one call.
Exit: one implementation per function code, used by UI and program engine alike.

P4 · Docs & UI

This document replaces the forum write-up; the register tool shows the resolved handle and last status.
Exit: help file and forum point at the same table.
07

Open decisions

  1. Do block reads return an array, or keep a separate call name, given the program engine has no array type for Modbus values?
  2. Does MB_DEFINE_DEVICE live in the program file or in the project database, so the UI and the program share handles?
  3. Is BIT a type, or an operator applied to a value?
  4. Are diagnostics 0x08 and exception status 0x07 in scope, or does the set stay at the four data areas?
  5. Should an oversized block write auto-split, or always return MB_ERR_RANGE and let the program split?
